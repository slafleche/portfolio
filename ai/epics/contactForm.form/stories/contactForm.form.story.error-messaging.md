# Story — Error handling and messaging

As a visitor using the contact form, when I press submit and there are problems, the system collects messages from the form shell and its blocks into message-centre transmissions. Each message has a severity (`error` / `warning` / `info`), an internal code, user-facing text, an optional higher-order summary derived from its category (for example, a global “invalid input” message), and optionally a `scrollTarget` pointing to where the UI should scroll and focus.

On each submit attempt, the message-centre layer (or an adjacent orchestration helper) runs a triage pass over all messages to select a single priority message, choosing by severity first and then by the logical order of fields (for example, name → email → message). That priority message is recorded alongside the full bundle of messages. The full bundle is passed to the message centre so it can render summaries, but at most one toast is surfaced per submission, based on the priority message’s higher-order summary message, rather than one toast per field-level error.

The same priority decision also drives recovery behaviour in the form. When validation fails, the form enters an “invalid” state: the real submit button remains disabled and its descriptive text is updated to explain that errors must be fixed before submitting (while still referring to “submit”), and a small “jump to first error” control appears near the submit area. Activating that control (or the initial failed submit flow) uses the priority message’s `scrollTarget` to scroll the relevant part of the UI into view and focus the associated block so the user can start fixing the problem. As the user edits and blocks re-evaluate, live validation clears `error` messages; once no error-type messages remain, the form leaves the invalid state, the jump control disappears, and the submit button returns to its normal behaviour.

When a submission attempt begins, the form first enters a submitting state and disables all interactive blocks before any payload is collected. In this state, it asks each block to validate; if any block reports itself invalid, the form does not call into payload helpers at all and instead uses the validation results for messaging and recovery, then exits the submitting state. Only when every block reports `valid === true` does the form proceed to collect per-block payload fragments, assemble the overall payload, and hand it to the submit helper while keeping the form disabled until the response returns.

When human verification (for example, the Turnstile block) cannot be loaded or configured correctly, the system treats this as a submission-blocking, catastrophic error rather than a normal validation problem. In this state, all form fields and the submit button are disabled so visitors do not spend time filling out a form that cannot be sent. The message-centre surfaces a single clear message explaining that human verification is unavailable and that the message cannot be sent right now, with guidance to try again later (for example, by closing and reopening the form or reloading the page). As long as this catastrophic condition remains, pressing submit does not attempt to contact the backend; once human verification initialises successfully on a future visit, the catastrophic message disappears and the form returns to normal behaviour. When this outage is due to external infrastructure (for example, Turnstile or email transport being down), the form maps it to the `form-status-service_unavailable` status. When it is due to misconfiguration within this application (for example, missing keys or required environment variables), the form maps it to the `form-status-not_configured` status.
