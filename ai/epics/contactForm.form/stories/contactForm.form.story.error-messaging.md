# Story — Error handling and messaging

As a visitor using the contact form, when I press submit and there are problems, the system collects messages from the form shell and its blocks into message-centre transmissions. Each message has a severity (`error` / `warning` / `info`), an internal code, user-facing text, a higher-level `categoryError` (for example, “invalid input”), and optionally a `scrollTarget` pointing to where the UI should scroll and focus.

On each submit attempt, the message-centre layer (or an adjacent orchestration helper) runs a triage pass over all messages to select a single priority message, choosing by severity first and then by the logical order of fields (for example, name → email → message). That priority message is recorded alongside the full bundle of messages. The full bundle is passed to the message centre so it can render summaries, but at most one toast is surfaced per submission, based on the priority message’s `categoryError`, rather than one toast per field-level error.

The same priority decision also drives recovery behaviour in the form. When validation fails, the form enters an “invalid” state: the real submit button remains disabled and its descriptive text is updated to explain that errors must be fixed before submitting (while still referring to “submit”), and a small “jump to first error” control appears near the submit area. Activating that control (or the initial failed submit flow) uses the priority message’s `scrollTarget` to scroll the relevant part of the UI into view and focus the associated block so the user can start fixing the problem. As the user edits and blocks re-evaluate, live validation clears `error` messages; once no error-type messages remain, the form leaves the invalid state, the jump control disappears, and the submit button returns to its normal behaviour.
